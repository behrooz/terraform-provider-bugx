bugx Terraform Provider

Overview

The bugx Terraform provider is a custom provider that enables you to manage bugx clusters, Helm releases, secrets, and query existing resources through the bugx API using Infrastructure as Code (IaC) principles.

🚀 Cluster Management

Create, read, update, and delete bugx cluster instances with full lifecycle management.

📦 Helm Release Management

Deploy and manage Helm charts on bugx clusters with version pinning support.

🔐 Secret Management

Create, update, and delete secrets via REST API with secure data handling.

🔍 Data Sources

Query existing clusters and resources without managing them in Terraform state.

🔄 Retry Logic

Automatic retry with exponential backoff for transient network errors.

⏱️ Configurable Timeouts

Customizable HTTP client timeouts and retry settings per provider instance.

Getting Started

This provider allows you to manage bugx infrastructure using Terraform. Before you begin, ensure you have:

  • Terraform installed (version 1.0 or later)
  • Go 1.22 or later (for building from source)
  • Access to the bugx API endpoint
  • Valid credentials for the bugx API

Installation

Build from Source

cd /home/behrooz/Projects/vcluster_terraform
go build -o terraform-provider-bugx

Install Locally for Terraform

Terraform expects the provider binary in a specific directory based on <hostname>/<namespace>/<type>/<version>/<os>_<arch>.

For a local provider with:

  • source: local/bugx/bugx
  • version: 0.1

Copy the binary like this (Linux amd64 example):

mkdir -p ~/.terraform.d/plugins/local/bugx/bugx/0.1/linux_amd64
cp terraform-provider-bugx ~/.terraform.d/plugins/local/bugx/bugx/0.1/linux_amd64/

Adjust the OS/arch folder name if necessary.

Provider Configuration

Configure the bugx provider in your Terraform configuration file: 

terraform {
  required_providers {
    bugx = {
      source  = "local/bugx/bugx"
      version = "0.1"
    }
  }
}

provider "bugx" {
  # Credentials used for POST /login. The provider will automatically
  # call /login, get the token from {"token": "..."} and send it as
  # the Authorization header on subsequent API calls.
  username = "admin"
  password = "admin"
  
  # Optional: Configure timeout (in seconds, default: 300)
  timeout = 300
  
  # Optional: Configure max retries for failed requests (default: 3)
  max_retries = 3
}

Provider Arguments

Argument Type Required Description
username string Required Username for login to bugx API
password string Required Password for login to bugx API (sensitive)
timeout integer Optional HTTP client timeout in seconds (default: 300)
max_retries integer Optional Maximum number of retries for failed requests (default: 3)
Note: The base URL is hardcoded to https://bugx.ir and cannot be configured.

Resources

bugx_cluster

Manages a bugx cluster instance. This resource creates, updates, and deletes bugx clusters through the bugx API.

Example Usage

resource "bugx_cluster" "example" {
  name             = "mycluster"
  control_plane    = "k8s"
  cpu              = "1"
  memory           = "1024"
  platform_version = "v1.31.6"
  cluster_type     = "tiny"
  coredns_cpu      = "0.5"
  coredns_memory   = "0.250Gi"
  apiserver_cpu    = "0.5"
  apiserver_memory = "0.250Gi"
}

Argument Reference

Argument Type Required Description
name string Required Name of the cluster
cluster_id string Optional Unique identifier for the cluster. If not provided, the API will generate one
control_plane string Required Control plane type (e.g., k8s)
cpu string Required CPU allocation for the cluster
memory string Required Memory allocation for the cluster (in MB or with unit like 1024)
platform_version string Required Platform version (e.g., v1.31.6)
cluster_type string Required Type of cluster (e.g., tiny, small, medium, large)
coredns_cpu string Required CPU allocation for CoreDNS (e.g., 0.5)
coredns_memory string Required Memory allocation for CoreDNS (e.g., 0.250Gi)
apiserver_cpu string Required CPU allocation for API server (e.g., 0.5)
apiserver_memory string Required Memory allocation for API server (e.g., 0.250Gi)
status string Optional Initial status of the cluster (default: Progressing)

Attribute Reference

Attribute Type Description
cluster_id string Computed Unique identifier for the cluster (populated after creation if not provided)
endpoint string Computed Cluster endpoint URL
namespace string Computed Kubernetes namespace where the cluster is deployed
kubeconfig string Computed, Sensitive Kubeconfig content for connecting to the cluster (only available when cluster status is Healthy)

Import

Clusters can be imported using the cluster ID:

terraform import bugx_cluster.example <cluster-id>
Notes:
  • The provider will automatically poll the cluster status after creation until it becomes Healthy
  • The kubeconfig attribute is only populated when the cluster status is Healthy
  • Cluster deletion requires both the cluster name and namespace

bugx_helm_release

Manages Helm releases on bugx clusters. This resource allows you to deploy and manage Helm charts with version pinning support.

Example Usage

resource "bugx_helm_release" "mysql" {
  cluster_name = bugx_cluster.devcluster.name
  namespace   = "default"
  release     = "mysql"
  chart       = "bitnami/mysql"
  repo        = "https://charts.bitnami.com/bitnami"
  chart_version = "8.0.0"  # Pin to specific version
  values_file = "${path.module}/helm-values/mysql-values.yaml"
  depends_on  = [bugx_cluster.devcluster]
}

Argument Reference

Argument Type Required Description
cluster_name string Required Name of the bugx cluster where the Helm release will be deployed
namespace string Required Kubernetes namespace for the Helm release
release string Required Name of the Helm release
chart string Required Helm chart name (e.g., bitnami/mysql)
repo string Required Helm repository URL
chart_version string Optional Specific chart version to pin (recommended for reproducible deployments)
values_file string Optional Path to Helm values file

bugx_secret

Manages secrets via the bugx API. This resource allows you to create, update, and delete secrets with secure data handling.

Example Usage

resource "bugx_secret" "example" {
  name        = "my-secret"
  description = "Example secret for testing"
  
  data = {
    username = "admin"
    password = "secret-password"
    api_key  = "sk-1234567890abcdef"
  }
}

# Output the secret metadata (data values are sensitive and won't be shown)
output "secret_id" {
  value = bugx_secret.example.id
}

output "secret_created_at" {
  value = bugx_secret.example.created_at
}

Argument Reference

Argument Type Required Description
name string Required Unique name for the secret
description string Optional Description of the secret
data map(string) Required Map of key-value pairs (marked as sensitive)

Attribute Reference

Attribute Type Description
id string Computed Unique identifier for the secret
created_at string Computed Timestamp when the secret was created
updated_at string Computed Timestamp when the secret was last updated

Import

Secrets can be imported using the secret ID:

terraform import bugx_secret.example <secret-id>
Note: The secret resource uses the /api/v1/secrets endpoint. Make sure your API base URL points to the correct server.

Data Sources

bugx_cluster

Query existing clusters without managing them in Terraform state. This is useful for referencing existing clusters or getting cluster information for use in other resources.

Example Usage

data "bugx_cluster" "existing" {
  name = "mycluster"
}

output "cluster_status" {
  value = data.bugx_cluster.existing.status
}

output "cluster_endpoint" {
  value = data.bugx_cluster.existing.endpoint
}

Argument Reference

Argument Type Required Description
name string Required Name of the cluster to query

Attribute Reference

The data source exports all attributes available from the cluster resource, including:

  • cluster_id - Unique identifier for the cluster
  • status - Current status of the cluster
  • endpoint - Cluster endpoint URL
  • namespace - Kubernetes namespace
  • platform_version - Platform version
  • And other cluster attributes

Best Practices

1. Use Version Pinning

Always pin specific versions for Helm charts to ensure reproducible deployments: 

chart_version = "8.0.0"  # Pin to specific version

2. Secure Credentials

Never commit credentials to version control. Use environment variables or Terraform Cloud/Enterprise: 

provider "bugx" {
  username = var.bugx_username
  password = var.bugx_password  # Mark as sensitive
}

3. Use Dependencies

Always use depends_on to ensure resources are created in the correct order: 

resource "bugx_helm_release" "app" {
  depends_on = [bugx_cluster.example]
  # ...
}

4. Handle Sensitive Data

Mark sensitive outputs and use appropriate file permissions for kubeconfig files: 

resource "local_file" "kubeconfig" {
  file_permission = "0600"  # Read/write for owner only
  # ...
}

5. Configure Timeouts

Adjust timeouts based on your cluster creation times: 

provider "bugx" {
  timeout = 600  # 10 minutes for large clusters
}

Troubleshooting

Common Issues

1. Authentication Failures

Problem: Login fails with 401 Unauthorized
Solution: Verify your username and password are correct. Check that the API endpoint is accessible.

2. Cluster Creation Timeout

Problem: Cluster creation times out
Solution: Increase the timeout value in the provider configuration. Large clusters may take longer to become healthy.

3. Kubeconfig Not Available

Problem: kubeconfig attribute is empty
Solution: The kubeconfig is only available when the cluster status is Healthy. Wait for the cluster to become healthy before accessing the kubeconfig.

4. Network Errors

Problem: Transient network errors during API calls
Solution: The provider includes automatic retry logic with exponential backoff. You can adjust max_retries in the provider configuration.

5. Import Failures

Problem: Unable to import existing resources
Solution: Ensure you're using the correct resource ID format. For clusters, use the cluster ID. For secrets, use the secret ID.

Debugging Tips

  • Enable Terraform debug logging: TF_LOG=DEBUG terraform apply
  • Check API response codes and error messages in the logs
  • Verify network connectivity to the bugx API endpoint
  • Ensure the provider binary is in the correct location
  • Check Terraform version compatibility
